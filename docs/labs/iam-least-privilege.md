# IAM Least-Privilege Lab

Implement IAM groups with least-privilege permissions to control support
engineers' access to AWS resources.

## Objective

Give a support engineer read-only visibility into EC2 (and later RDS) while
denying all mutating actions — then **prove** it by getting a 403.

## Steps completed

1. **Created the IAM group** `SupportEngineers` and attached the AWS managed policy
   `AmazonEC2ReadOnlyAccess`.
   ![SupportEngineers group created](../images/35-iam-group-created.png)
2. **Created the IAM user** `support-engineer-1` via "Add user to group," joining it
   to `SupportEngineers`. Retrieved console credentials (account sign-in URL +
   autogenerated password).
   ![Create user — set permissions](../images/36-iam-create-user-permissions.png)
   ![User created successfully](../images/39-iam-user-created.png)
3. **Signed in as `support-engineer-1`** in a separate session. The "Choose AWS
   sessions" screen was confusing ("Which do I choose?") — resolved by clicking
   **Add session** to start a fresh session as the IAM user.
   ![IAM user sign-in page](../images/42-iam-user-signin.png)
   ![Choose AWS sessions dialog](../images/43-choose-sessions.png)
4. **Reviewed the security-credentials tab** for `support-engineer-1` (console
   password, MFA status, access keys).
   ![Security credentials tab](../images/41-iam-security-credentials.png)
5. **Verification — the 403 proof:** attempted to terminate an EC2 instance as
   `support-engineer-1`. The attempt was denied with error code 403 —
   `ec2:TerminateInstances` not allowed. Read-only access otherwise worked.
   This is default-deny doing its job.
   ![403 termination denied](../images/44-iam-403-denial.png)
6. **DIY extension:** attached `AmazonRDSReadOnlyAccess` to `SupportEngineers`
   (typing the policy name and pressing Enter in the search box) so the group can
   view RDS info. Validation confirmed the group carried both
   `AmazonEC2ReadOnlyAccess` and `AmazonRDSReadOnlyAccess`.
   ![DIY — grant RDS read access](../images/45-diy-rds-read-access.png)
   ![DIY validation form](../images/46-diy-validation-form.png)

## Key takeaways

- **Default deny is the foundation.** Everything in AWS is denied unless a policy
  explicitly allows it — attaching only read-only policies means mutating calls
  fail closed with 403.
- **Groups scale, users don't.** Permissions attach to groups (`SupportEngineers`),
  and users inherit them by membership. Onboarding = "add user to group."
- **Verification is part of the work.** A policy isn't done until you've tested both
  that allowed actions work and that denied actions fail.
